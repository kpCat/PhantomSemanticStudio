# PSS-003 — правила компиляции в staging XML (fail closed)

## Приём кандидатов

1. Создавать StagePlan только для **явно выбранных** ID; первое UI-решение может выбирать весь список APPROVED, но пользователь должен увидеть количество, IDs и получить отдельный Yes/No. DRAFT/REJECTED никогда не становятся XML. Если среди выбранных есть изменённый approval, несовместимая запись либо source drift — **отклонить весь batch**, перечислить причины и ничего не записывать в finished stage.
2. Source stamp сверять повторным чтением ровно импортированных файлов, а не только сохранённой памятью. Использовать `SourceFingerprint`, `ApprovedFingerprint` и `CandidateReview.IsCurrent`, `CandidateValidator.Validate(..., allPeers)`; смешанные original/current source запрещены. Проверить источник ДО копирования и ПОСЛЕ записи stage, а также каждый SHA скопированных байтов.
3. Разрешённые kinds: `PATTERN` → `my-social-topics.xml`, `TEMPLATE` → `my-phrases.xml`. Только уже существующая topic/act-связка и разговорный `act`; запрет `support.*`, `identity.*`, `party.*`, `item.*` и любых функциональных unknown/new intent. Конфликт одно и того же normalization key между чужими act → fail. Никаких новых acts/topics/alias/fact/recall/virtual commands.
4. **Никаких gender-specific templates**: только `Gender=ANY`, независимо от kind, пока Java runtime не имеет фильтра в обычном template selector. Текст не изменять и не приводить ANY автоматически. Никакого формального gender-safety обещания. Промпт и ручное ревью сохраняют своё значение.
5. В PSS-003 запрещены все placeholders (`{name}`, `{value}`, `{memory}`, `{interest}`) в выбранной партии — это осознанное консервативное ограничение staging compiler. Запрещены multiline/control, DOCTYPE, XML literal/markup, математические/Unicode-невидимые управляющие символы. Не подменять текст и не обрезать длину.
6. После нормализации Java-style PATTERN должен укладываться в 160 Java UTF-16 char; TEMPLATE должен укладываться в **240 UTF-8 bytes**, даже если C# предварительно принимал 180 code points. Корректная XML escaping выполняется стандартным XML API; кодировка строго UTF-8 с настоящей кириллицей. Без `&#x04xx;` для обычной кириллицы, без `\\u04xx`.
7. Внутри stage существующие core/custom records остаются: append new entries only with `override="false"`, generated deterministic valid key based on candidate immutable 32-hex ID, no collision, no unbounded growth. Существующий custom override `true` сохраняется; никогда не заменять существующий ID молча. Limit каждого target XML 65,536 bytes включая существующий текст; суммарные catalog limits строго сверять. При переполнении — `CAPACITY/FILE_SIZE`, не повышать лимиты.
8. **Редакционная безопасность не доказывается автоматически.** Перед staged export пользователь отдельно подтверждает: (a) нет мата/adult, (b) нет гендерных оборотов, специфичных только одному полу, (c) не обещаются игровые действия, лут, телепорты или несуществующая память, (d) он понимает «не для установки». Без явного Yes — отмена. Дополнительные лексические фильтры могут только предупреждать/блокировать; не делать вид, что NLU/semantic duplicate доказаны. `profanity="NONE"` — предварительная редакционная метка только внутри stage; ни Java schema-validity, ни regex не доказывают semantic correctness.
9. Входные XML custom файлы парсить без DTD/XXE, с закрытым Resolver; отклонять неизвестные/потенциально опасные атрибуты через existing parser/Java proof. Если staging writer изменяет нецелевые SHA или теряет даже комментарии/существующие overrides в target XML — fail и исправление до принятия.
10. Stage статус `STAGED_UNVALIDATED` до явной успешной Java-пробы. После Java PASS `JAVA_CONTENT_VALIDATED_NOT_SERVER_READY`. На status смены исходного файла старый stage не переиспользовать; создавать новый. Никакого кнопочного Install/Apply/Publish и никакого clipboard/manual copy-instruction для прямого замещения L2J.

## Операционная атомарность

- Использовать уникальный staging каталог с временной меткой `.partial` внутри защищённого workspace. Сначала записать все данные, проверить копию и все approvals/hash/bytes, только потом атомарно обозначить готовый stage (rename внутри того же filesystem). Не перезаписывать другой stage. Ошибка и Cancellation → отсутствие finished stage, аккуратная уборка только собственного `.partial` после проверки exact root.
- Названия каталогов и IDs — generated, без сырого user/model текста и без произвольных path separators.
- Подозрительные пути, junction, symlink и source==workspace конфликтуют fail closed. OS-level hostile TOCTOU полностью не решён — не заявлять защиту от злонамеренного concurrent процесса.
