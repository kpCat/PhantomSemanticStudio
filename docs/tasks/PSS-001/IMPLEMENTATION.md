# Реализация PSS-001

## 1. Сборка и UI
Запустить `scripts/Build-Verify.ps1`. Исправить реальные compiler/test ошибки минимально, не переписывая весь starter. Не объявлять C# tests пройденными по текстовому сканированию.
Открыть MainForm в VS Designer, проверить шесть вкладок и сохранение/повторное открытие. Constructor только InitializeComponent. Если нет UI-доступа, отдельно `NOT_TESTED_DESIGNER` — это незакрытый gate, не PASS. Не закрывать чужой VS и не переключать его текущий solution. Runtime smoke проводить в отдельном окне приложения.
Визуально проверить минимум 100% и 150% DPI, читаемость полей, отсутствие налезания кнопок/обрезания текста, изменение размера. Сохранить стандартные controls и `.Designer.cs/.resx`, не вводить runtime BuildUi, кастомный рендер или Visual Studio dependencies.

## 2. Безопасный import и отчёт
Прочитать только actual High Five humanized v1/v2/v3/custom и manifest. Зафиксировать SHA каждого прочитанного файла до/после проверки, counts (effective patterns/templates/aliases, тематики, предупреждения), actual local Git HEAD read-only при наличии. Не менять checkout и не рекурсировать все хроники.
PackReader — инспектор, не полный Java-validator. Уточнить диагностику unsupported/schema элементов, не терять данные тихо и не выдавать approximate модель за Java parity. Перепроверить custom override порядок и конфликтные aliases. Регрессионные fixtures остаются небольшими и вымышленными; не коммитить весь реальный пак в новый репозиторий.

## 3. Кандидаты и dedup
Подтвердить exact duplicate по NFKC/ru lower/ё→е/punctuation для исходника и рабочего набора. Near-duplicate показывать как лексическое предупреждение с конкретным текстом и ID; не называть это доказанным смысловым dedup.
Проверка потенциальных смысловых повторов должна иметь явный статус `не проверено` до настоящего отдельного механизма. Не подключать неназванную embedding-модель и не предполагать, что Gemma является embedding endpoint.
Редактирование отменяет approval, повторная генерация не перезаписывает кандидатов, immutable fingerprint/source binding проверяется на экспорте. Не делать одобрение всех одной кнопкой. Утверждение «я бафнул/выдал предмет» нельзя принимать за подтверждение игрового действия.
Если модель или ручная правка содержит ненормативную лексику, неизвестную подстановку или несовместимое условие, не маркировать такую реплику автоматически как безопасную `profanity=NONE`. Для starter блокировать соответствующий XML-export и выдавать понятное предупреждение. Полноценный profanity/mature authoring — не эта задача.

## 4. Диалог и замечания
Сохранить чёткое различие «каталожный инспектор» и «реальный сервер». Не подменять ответы пака ответами Gemma и не выдавать хорошие ответы модели за новую способность сервера.
Добавить выбор/просмотр ранее сохранённого замечания и кнопку явного применения в конструктор. Замечание не применяется автоматически ко всем темам. Его scope (topic/act/пол/отношения) должен быть виден; при смене source baseline требовать новое ревью, не привязывать молча.
Никакой записи в игру, `conversation.personal` или profile DB. Пол и темперамент — редакционные ограничения/пожелания, не доказанные server filters.

## 5. LM Studio
Endpoint `http://127.0.0.1:1234/v1`, identifier `gemma-4-26b-a4b-it-ultra-uncensored-heretic`; endpoint/model остаются редактируемыми. Проверить exact ID через `/models`, не выбирать другую модель автоматически.
Один реальный запрос на 4–6 кандидатов; доказать strict JSON или зафиксировать точный ответ/ошибку. Не ослаблять контракт молча при unsupported JSON Schema. API token только в памяти, исключить из отчёта/ZIP. Timeout/cancel, finish_reason=length, malformed/fenced/extra-key JSON, response cap, HTTP 4xx/5xx — негативные tests с fake handler.
Никакого shell/tools/кодогенерации от Gemma. Модель не выбирает target paths, ID, override или publication permission. Не отправлять ей весь репозиторий.

## 6. Export
Оставить только отдельный ZIP `REVIEW_ONLY_NOT_SERVER_VALIDATED`, baseline, одобренный JSON и явно предварительные XML-фрагменты. Возможен отказ от XML-фрагментов, если они не могут быть честно размечены: JSON + замечания лучше ложного «готового XML».
Source drift, stale approval, blank note, invalid candidates и пол без runtime-filter проверяются перед экспортом. Глобальные лимиты, будущие bucket limits и полнота grammar/profanity coverage не считаются доказанными обычной C#-проверкой.
Не добавлять manifest installer, `Apply`, замену исходных файлов, auto reload или попытку запустить Java/Ant в рабочей High Five. Следующий этап может построить Java bridge в изолированной копии, но не сейчас.

Допустимые изменения: собственные src/**, tests/**, scripts/**, docs/**, README, AGENTS при сохранении запретов, solution/project metadata и новый отчёт. Не удалять BASELINE_MANIFEST и не переписывать исходный verification report как будто он изначально был GREEN.
Не вводить SQL/SQLite, web front-end, внешнюю агентную инфраструктуру и package upgrades «заодно». Документировать реальные ограничения и дальнейший PSS-002.
